---
 
## Relationship Descriptions
 
| Relationship | Type | Description |
|---|---|---|
| User → LoyaltyProfile | One-to-One | Each customer has exactly one loyalty profile |
| LoyaltyProfile → Tier | Many-to-One | Many customers share one tier level |
| User → Transactions | One-to-Many | A user can have unlimited transaction records |
| User → Redemptions | One-to-Many | A user can redeem multiple rewards |
| User → UserBadges | One-to-Many | A user can earn multiple badges |
| UserBadge → Badge | Many-to-One | Many users can hold the same badge type |
| Redemption → RewardCatalog | Many-to-One | Many redemptions can reference one reward |
 
---
 
## Key Design Decisions
 
1. **LoyaltyProfile is separate from User** — keeps loyalty data isolated and allows the same user entity to be reused across other contexts (Admin, Brand Manager never have profiles).
2. **Transaction records every point movement** — both earn and redeem operations create transactions with before/after balances, providing a full audit trail.
3. **Redemption is distinct from Transaction** — redemptions carry voucher codes, fulfillment status, and expiry; the corresponding point deduction is a separate Transaction record linked by description.
4. **PointsRule drives earning logic** — earning points calls the rule engine rather than hardcoding rates, making business rules manageable from the Admin panel.
5. **Campaign is independent** — campaigns layer on top of rules (multipliers, bonuses) and are checked at earn time to apply promotional boosts.
